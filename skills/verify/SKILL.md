# verify — 完成機能の自動検証

## このスキルの役割

`docs/design/<feature-slug>/` の設計ドキュメントと implementation-log.md を読み、実装が要件を満たしているか体系的に検証する。検証結果は `verification-report.md` に出力し、未充足項目があれば実装担当（ユーザーまたは `implement` Skill）にフィードバックする。

## 検証する観点

| カテゴリ | 内容 | 失敗時の扱い |
|---------|------|-------------|
| 静的解析 | 型チェック / リント / フォーマット | 即時報告、修正提案 |
| ユニットテスト | 既存および新規テストの実行 | 失敗テストを特定 |
| 統合テスト | 要件をまたぐ振る舞い | シナリオ単位で報告 |
| 受け入れ基準 | requirements.md の Given/When/Then | 各項目 PASS/FAIL/N/A |
| 設計整合性 | basic/detailed-design との差分確認 | 差分を列挙 |
| 非機能要件 | 性能・セキュリティ・アクセシビリティなど | 確認可能な範囲で |

## 使い方

### ステップ 1: 入力の読み込み

1. ユーザーから機能名（スラグ）を受け取る。
2. 以下を読む。
   - `docs/design/<feature>/requirements.md` — 受け入れ基準の根拠
   - `docs/design/<feature>/detailed-design.md` — 検証観点
   - `docs/design/<feature>/implementation-log.md` — 何が実装されたか、検証用メモ
3. プロジェクトのテスト・リント・ビルドコマンドを把握する（`package.json`, `Makefile`, `CLAUDE.md` などを参照）。

**入力が不足している場合の対応:**

| 状態 | 推奨アクション |
|------|--------------|
| `docs/design/<feature>/` が無い | 検証範囲が不明なため停止。ユーザーに「何を検証したいか」を確認するか、`git diff` / 直近コミットから対象を推定してよいか合意を取る |
| requirements.md が無い | 受け入れ基準が無いため PASS/FAIL 判定不能。implementation-log.md から「何を実装したか」だけでも検証する旨を明示 |
| implementation-log.md が無い | 検証コマンドが不明。README / package.json / Makefile から推測し、それを使う旨をレポートに明記 |
| すべて揃っている | そのまま進む |

入力不足の場合、検証レポートの先頭に **「前提資料の不足」** セクションを設け、何が無かったか・どう代替したかを必ず記録する。

### ステップ 2: 検証計画の作成

requirements.md の機能要件 (FR-XX) と受け入れ基準を抽出し、それぞれに対応する検証手段を決める。

| 受け入れ基準 | 検証手段 | コマンド / 手順 |
|-------------|---------|----------------|
| FR-01 AC1 | ユニットテスト | `pnpm test login.test.ts` |
| FR-02 AC1 | E2E テスト | `pnpm test:e2e auth.spec.ts` |
| 非機能 性能 | 計測 | `pnpm bench` |
| FR-03 AC1 | 手動確認 | implementation-log の手順をなぞる |

TaskCreate で各検証項目をタスク化する。

### ステップ 3: 自動検証の実行

以下を順に実行し、結果を記録する（順序は実行コストの低い順）。

1. **フォーマット / リント**: 失敗なら、指摘箇所を要約。auto-fix できるものは提示するだけで適用しない（ユーザー判断に委ねる）。
2. **型チェック**: TypeScript なら `tsc --noEmit`、Python なら `mypy` など。
3. **ユニットテスト**: 全体ではなく該当機能に関連するスコープから先に。落ちたら詳細をキャプチャ。
4. **統合 / E2E テスト**: 実装ログに書かれたコマンドを使う。
5. **ビルド**: 必要ならプロダクションビルドが通るか。

各コマンドの実行は **必ず実装ログ・README・package.json から実コマンドを確認してから**。推測で実行しない。

### ステップ 4: 受け入れ基準の確認

requirements.md の各 AC について PASS / FAIL / N/A を判定する。

- **PASS**: 自動テストで担保されている、または手動確認で動作を確認できた
- **FAIL**: テストが落ちた、または期待通りに動かない
- **N/A**: 検証対象外（スコープ外、他チーム責務など）
- **NOT_VERIFIED**: 自動も手動も実行不能（環境がない等）。理由を必ず記載

UI を伴う AC は、可能なら開発サーバーを起動して動作を確認する（`implement` の検証用メモ参照）。起動できない場合は明示的に NOT_VERIFIED とする。

### ステップ 5: 設計整合性チェック

- 実装されたファイルが detailed-design.md のファイル構成と一致しているか
- 関数シグネチャや API スキーマが設計と一致しているか
- implementation-log.md の「設計との差分」セクションに、未承認の差分が入っていないか

差分があれば列挙し、それが意図的か否か判別する。

### ステップ 6: レポート出力

`docs/design/<feature>/verification-report.md` を以下のテンプレートで生成・更新する。

````markdown
# 検証レポート: <機能名>

検証日時: <YYYY-MM-DD HH:MM>
検証者: verify skill
対象コミット: <git rev-parse HEAD の結果>
総合判定: ✅ PASS / ⚠️ PARTIAL / ❌ FAIL

## サマリ
- 受け入れ基準: <PASS数>/<総数> PASS, <FAIL数> FAIL, <NA数> N/A
- ユニットテスト: <PASS数>/<総数>
- 型チェック: ✅ / ❌
- リント: ✅ / ❌

## 受け入れ基準の検証結果
| ID | 受け入れ基準 | 結果 | 検証手段 | 備考 |
|----|-------------|------|---------|------|
| FR-01 AC1 | ログイン成功時にトークンが返る | ✅ PASS | `pnpm test login.test.ts` | |
| FR-01 AC2 | パスワード誤りで401 | ❌ FAIL | テスト失敗 | 期待 401 vs 実際 500 |

## 自動検証コマンドの実行結果
### `pnpm lint`
✅ PASS

### `pnpm typecheck`
✅ PASS

### `pnpm test`
❌ FAIL — 1 件失敗
```
FAIL src/auth/login.test.ts
  ● login > rejects invalid password
    expected 401, received 500
```

## 設計との差分
- detailed-design.md ではエラー時 401 を返す仕様だが、実装では 500 が返っている

## 推奨アクション
1. ❌ FAIL: パスワード誤り時のステータスコード修正 (src/auth/login.ts)
2. ⚠️ 未検証: 性能要件 (実環境がないため計測不能) — 本番デプロイ後に再検証

## 次に実行すべきこと
- `implement` Skill で上記 FAIL 項目を修正後、再度 `verify` を実行
````

## 進め方の原則

- **コマンドを推測しない**。実装ログ・README・設定ファイルから実コマンドを確認してから実行する。
- **失敗を隠さない**。テストが落ちたら、それを正直にレポートに記載する。「ほぼ動いている」と曖昧にしない。
- **検証できないものは検証できないと書く**。NOT_VERIFIED を活用する。
- **修正は基本しない**。verify Skill の役割は検証とレポート。修正は `implement` Skill またはユーザーに任せる。ただし軽微な lint 修正など、ユーザーが許可した範囲なら可。
- **レポートは差分追記でなく上書きで良い**。verification-report.md は最新の検証結果を表す。過去ログが必要なら git history で追える。
- 結果報告時は「総合判定」「主要な失敗項目」「次のアクション」を簡潔に口頭で伝え、詳細はレポートファイルを参照させる。
