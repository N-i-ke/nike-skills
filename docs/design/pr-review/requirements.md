# 要件定義: PR Review

最終更新: 2026-05-08
ステータス: ドラフト

## 1. 背景・目的

nike-skills プラグインは現状 design / implement / verify / investigate の4 Skill を提供しているが、コードがマージされる直前の **PR レビュー** に特化した Skill は存在しない。組み込みの `/review` skill はあるが、以下のニーズが満たされていない:

- **一貫体験**: design → implement → verify と続く流れの最後に、`pr-review` を組み込みたい。設計ドキュメント (`docs/design/<feature>/`) との整合性を自動でチェックできるのは nike-skills 専用 Skill だけ。
- **セルフレビュー**: 自分が出した PR を、第三者視点を擬似的に取り入れてレビューしたい。マージ前に観点抜けを潰したい。
- **他者レビュー支援**: 他人の PR をレビューする際、観点抜けを防ぎ短時間で重要箇所に集中したい。
- **CLAUDE.md の暗黙契約**: プロジェクト固有の制約（例: `nike.py ↔ templates ↔ SKILL.md` の三点整合、`Co-Authored-By: Claude` を付けない、など）を毎回手で確認するのは漏れが起きやすい。

これらを **`pr-review` Skill** + 必要に応じた **nike CLI 拡張** で支援する。

## 2. スコープ

### 対象
- ローカルブランチの差分 (`git diff <base>...HEAD`) のレビュー
- GitHub 上の PR (`gh pr view <num>` 経由) のレビュー
- 観点別チェック: ドキュメント整合、セキュリティ、可読性、運用面、拡張性、テスト網羅、コミットメッセージ、CLAUDE.md の暗黙契約
- レビューレポートのチャット出力（既定）
- ユーザー許可時の GitHub PR コメント投稿（`gh pr comment` / `gh pr review`）
- 既存 nike-skills 設計ドキュメントとの整合確認（`docs/design/<feature>/` がある場合）

### 対象外
- 静的解析ツールの新規実装（既存の lint / typecheck / test を呼び出すのみ）
- コード自動修正（指摘のみ。修正は implement Skill またはユーザーに任せる）
- レビュー結果の永続的な統計収集・ダッシュボード化
- 複数 PR を横断したマージ順序の調整
- マージ操作の自動実行（`gh pr merge` は呼ばない）
- 機密情報を外部サービスへ送信する操作

## 3. ユーザーストーリー

- US-01: nike-skills 利用者として、自分のフィーチャーブランチで PR を出す前にセルフレビューを走らせたい。なぜなら、設計ドキュメントと実装の乖離・観点抜けをマージ前に潰したいから。
- US-02: チームメンバーとして、他人の GitHub PR を観点抜けなくレビューしたい。なぜなら、短時間で重要な指摘を漏れなく出したいから。
- US-03: nike-skills 利用者として、design / implement で生成した `docs/design/<feature>/` と現在の実装の整合性を自動で見たい。なぜなら、設計通りに実装されたかを目視チェックする手間を減らしたいから。
- US-04: 開発者として、PR コメントへの自動投稿は許可制にしたい。なぜなら、誤ったレビューを GitHub 上に公開したくないから。
- US-05: プロジェクトメンテナとして、CLAUDE.md に書いた暗黙契約（三点整合、コミット規約など）を PR レビュー時に毎回チェックしてほしい。なぜなら、暗黙契約は壊れても CI で検出されないものが多く、レビュー時に拾うしかないから。
- US-06: AI トークンを節約したい開発者として、差分パース・コミット履歴取得・PR メタデータ取得などの決定的処理は CLI に肩代わりさせたい。なぜなら、Claude の往復回数とトークンを抑えたいから。

## 4. 機能要件

### FR-01: レビュー対象の特定
**説明**: ユーザー指示に応じてローカル差分または GitHub PR をレビュー対象として特定する。

**受け入れ基準**:
- Given ユーザーが「セルフレビュー」または対象 PR 番号を指定しない場合, When pr-review Skill を起動する, Then 現在のブランチと `git merge-base` で算出した base からの差分をレビュー対象に決定する
- Given ユーザーが PR 番号 (例 `#42`) または PR URL を指定した場合, When pr-review Skill を起動する, Then `gh pr view <num>` の情報と `gh pr diff <num>` の差分をレビュー対象に決定する
- Given 現在ディレクトリが git リポジトリでない場合, When pr-review Skill を起動する, Then エラーを返してユーザーに伝える

### FR-02: 設計ドキュメントとの整合チェック
**説明**: `docs/design/<feature>/` が存在する場合、requirements.md / detailed-design.md と差分の整合をチェックする。

**受け入れ基準**:
- Given 差分内のファイルパスから推定される feature slug が `docs/design/` 配下に存在する場合, When 整合チェックを実行する, Then requirements.md の FR-XX 単位で「実装あり / 実装なし / 設計外の追加」を分類して報告する
- Given `docs/design/<feature>/` が存在しない場合, When 整合チェックを実行する, Then 「設計ドキュメント未検出」として該当チェックをスキップしレポートに明記する

### FR-03: セキュリティ観点のチェック
**説明**: 差分から代表的なセキュリティリスクを検出する。

**受け入れ基準**:
- Given 差分にハードコードされた認証情報・APIキー・トークンらしき文字列が含まれる場合, When セキュリティチェックを実行する, Then 該当箇所をファイル名と行番号付きで指摘する
- Given 差分にコマンド実行 (`subprocess` / `eval` / `child_process.exec` 等) または SQL 文字列結合がある場合, When セキュリティチェックを実行する, Then 入力検証の有無を確認するよう注意喚起する
- Given 差分にユーザー入力を扱う API ハンドラ追加がある場合, When セキュリティチェックを実行する, Then 認証・認可・入力バリデーションの有無を確認するよう促す

### FR-04: 可読性・保守性の観点
**説明**: コードの可読性・命名・複雑度・コメント・テストの観点をチェックする。

**受け入れ基準**:
- Given 差分内に新規追加された関数・クラスがある場合, When 可読性チェックを実行する, Then 命名・責務の明確さ・サイズ（行数）・コメント有無を観点として指摘候補を出す
- Given 差分内に新規追加されたパブリック関数がある場合, When テスト網羅チェックを実行する, Then 対応するテストファイルが diff に含まれているか確認し、無ければ警告する

### FR-05: 運用面・拡張性の観点
**説明**: ログ・エラーハンドリング・設定値ハードコード・後方互換性・拡張ポイントをチェックする。

**受け入れ基準**:
- Given 差分にエラーハンドリング (try/except, try/catch) の追加・変更がある場合, When 運用チェックを実行する, Then ログ出力・例外の握りつぶし・上位への伝搬の妥当性を観点として指摘候補を出す
- Given 差分にマジックナンバーやハードコードされた URL / パス / 環境依存値がある場合, When 運用チェックを実行する, Then 設定外出しの提案を指摘する
- Given 差分が公開 API / CLI コマンド / 設定ファイル形式の破壊的変更を含む場合, When 拡張性チェックを実行する, Then 後方互換性とマイグレーション戦略を確認するよう促す

### FR-06: CLAUDE.md 暗黙契約のチェック
**説明**: プロジェクト直下の CLAUDE.md があれば読み込み、その中で明示された制約・規約に違反しそうな差分を指摘する。

**受け入れ基準**:
- Given プロジェクト直下に CLAUDE.md が存在する場合, When pr-review Skill を起動する, Then CLAUDE.md を読み込んで「暗黙契約」「規約」「禁止事項」のセクションを抽出しレビュー観点に追加する
- Given CLAUDE.md に「Co-Authored-By: Claude を付けない」などコミット規約が書かれている場合, When コミットメッセージをレビューする, Then 規約違反コミットを指摘する

### FR-07: レビューレポートの生成と出力
**説明**: 観点別の指摘を集約したレポートをチャットに出力する。

**受け入れ基準**:
- Given レビューが完了した場合, When レポートを生成する, Then 「総合判定 (APPROVE / COMMENT / REQUEST_CHANGES)」「観点別の指摘一覧」「強み (良い点)」「次のアクション」を含むレポートをチャットに出力する
- Given 各指摘について, When レポートに記載する, Then 「観点」「重要度 (blocker / major / minor / nit)」「ファイル:行」「現状」「提案」を含める
- Given レビュー対象が大きい場合 (例: 50 ファイル超), When レポートを生成する, Then `docs/reviews/<slug>/report.md` にも保存し、チャットにはサマリだけ出してファイルパスを案内する

### FR-08: GitHub への投稿（許可制）
**説明**: ユーザーが明示的に許可した場合のみ、GitHub PR にコメントを投稿する。

**受け入れ基準**:
- Given ユーザーが投稿許可を明示していない場合, When レビューが完了する, Then チャットに出力するのみで `gh pr comment` / `gh pr review` を実行しない
- Given ユーザーが投稿を許可した場合, When 投稿を実行する, Then 投稿先 PR 番号・投稿モード (`COMMENT` / `APPROVE` / `REQUEST_CHANGES`) を確認したうえで `gh pr review` を実行し結果を報告する
- Given gh 認証が無い・PR が見つからない等の失敗が起きた場合, When 投稿を試みる, Then 投稿失敗をエラーとしてレポートに記録する

### FR-09: nike CLI への決定的処理の委譲
**説明**: 差分パース・PR メタデータ取得・観点別チェック支援を nike CLI のサブコマンドとして提供し、AI トークン消費を抑える。

**受け入れ基準**:
- Given pr-review Skill が差分情報を必要とする場合, When `nike review-context [<pr>]` を実行する, Then 差分ファイル一覧・追加削除行数・base/head SHA・PR メタ (PR 指定時) を JSON で返す
- Given pr-review Skill がレポート雛形を必要とする場合, When `nike review-init <slug>` を実行する, Then `docs/reviews/<slug>/report.md` に観点別セクション入りの雛形を生成する
- Given nike CLI がエラーを返す場合, When Skill が CLI を呼び出す, Then JSON 構造を保ったエラー (`{"error": "..."}`) を受け取り、Skill 側でユーザーに伝える

## 5. 非機能要件

| カテゴリ | 要件 | 指標 |
|---------|------|------|
| 性能         | 中規模 PR (≦100 ファイル / ≦3,000 行) のレビューを 5 分以内に完了 | 通常的なローカル実行で計測 |
| 可用性       | gh / git の不在・認証切れに対し明確なエラーを出して中断 | 該当時に panic せず JSON エラー |
| セキュリティ | レビュー結果に検出した認証情報を **そのまま** 含めず、マスクする / 抜粋にとどめる。GitHub への投稿はユーザー許可必須 | 投稿前に確認プロンプト |
| 保守性       | 既存 Skill (design/implement/verify/investigate) と同じディレクトリ構造・SKILL.md フォーマットに揃える | スキル追加 PR の差分が小さい |
| 互換性       | Python 3.9〜3.12、stdlib のみで動作。`gh` は >=2.0 を想定 | CI マトリクスでパス |

## 6. 制約条件

- **nike CLI への委譲**: 決定的処理は `scripts/nike.py` のサブコマンドとして実装する。Skill 側ではロジックを書かない。
- **Python stdlib のみ**: 既存方針に倣い、外部依存は導入しない。
- **gh CLI 経由**: GitHub API への直接 HTTP は行わない（認証を `gh` に委ねる）。
- **JSON 出力契約**: nike CLI は全サブコマンドで JSON を stdout に出す。エラー時も `{"error": "..."}` 形式を保つ。
- **Co-Authored-By: Claude を付けない**: コミット規約上の制約（CLAUDE.md より）。
- **main への直接 push 不可**: PR 経由で取り込む。
- **新サブコマンド追加時の三点整合**: `nike.py` を変更したら `skills/pr-review/SKILL.md`, `README.md`, `scripts/tests/test_nike.py` を併せて更新する。

## 7. 前提条件

- ローカル実行環境に `python3` (>=3.9), `git` (>=2.30), `gh` (>=2.0) がインストール済み。
- GitHub PR レビュー機能を使う場合、`gh auth login` 済み。
- レビュー対象が `docs/design/` を持つ feature の場合、design / implement Skill で生成された成果物が存在する。
- リポジトリの base ブランチは `main` を既定とする（`gh pr view` の `baseRefName` で上書き可）。

## 8. オープンイシュー

- 巨大 PR (>100 ファイル) でのトークン枯渇対策: ファイルグルーピングして分割レビューする方式の必要性を検証する。
- レビュー観点のテンプレ化: チェック観点を YAML / JSON で外部化し、プロジェクトごとにカスタムするか検討する（v0.4 以降のスコープ）。
- `gh pr review --request-changes` を AI 起動で出すべきか: 誤検知リスクが高ければ `COMMENT` 固定にする選択肢もあり。
